Approval Workflows Stuck in Inboxes

When an approval stalls, the first explanation is usually speed. Someone did not answer fast enough. The more useful question is different: who owns the queue before the reminder is sent?

It is 16:20 and a confirmed order is waiting. Sales has sent the discount for approval. Finance needs one field checked. Operations will not reserve stock until the approval is complete. The request is not missing. It is sitting in an inbox that nobody treats as part of the system.

From the outside, this looks like a people problem. Someone should answer faster. Someone should follow up. Someone should watch the shared mailbox more closely.

But most stalled approvals do not fail because people ignore their work. They fail because the workflow has no clear queue, no owner and no visible state. The company has a process on paper, but the operating system is still email.

The approval is not the whole workflow

A simple approval contains more than a yes or no. It contains a trigger, a data check, a decision, an exception path and a record of what happened. If any of those pieces is unclear, the approval becomes a chase.

This is why reminders often disappoint. They make the delay louder without changing the shape of the work. The person receiving the reminder may still need to know which customer record is correct, whether the ERP price is current, who can approve the exception or whether the request has already been handled elsewhere.

The operational problem is not silence. It is ambiguity.

The practical test: Pick one approval that slowed down last week. Can you see when it entered the queue, who owned it, what data was missing, who decided, and what changed afterwards? If not, the workflow is not yet controlled.

Why inbox approvals feel harmless

Email is attractive because everyone already knows how to use it. A request can start quickly. A manager can reply from a phone. A copy can go to finance, sales and operations at the same time.

That convenience is real. It is also why the problem stays hidden for so long.

An inbox does not show process state. It shows messages. It does not know whether an approval is new, blocked, delegated, rejected, expired or already applied in the ERP. It does not enforce required fields. It does not keep a clean link between the decision and the system record that depends on it.

When volume is low, people compensate. They remember who usually answers. They search old threads. They ask across chat. When volume grows or a key person is away, the informal memory breaks.

Make the queue visible before you automate

The better answer is not to automate every approval immediately. First, make the queue visible. A visible queue turns a vague delay into a specific operating question.

For most B2B approval workflows, that means defining five things.

1. The trigger

Write down exactly what starts the approval. A discount above a threshold. A credit limit change. A manual price override. A delivery promise before stock is confirmed. If the trigger is vague, requests will enter the process too early, too late or not at all.

2. The required data

An approval should not ask a manager to search for context. The request should carry the customer, order, product, amount, reason, source system and proposed change. Missing data should block the request before it reaches the decision maker.

3. The owner

Every approval needs one current owner. Not a department. Not a shared mailbox. One accountable person or role at each step. Ownership can move, but it should never disappear.

4. The exception path

Real operations always contain exceptions. A key person is away. The ERP record is incomplete. The customer needs an answer before the next scheduled run. Define what happens then, otherwise exceptions become private negotiations.

5. The system record

The decision must end where the work continues. If the approval affects Salesforce, the ERP or both, the final state should be written back clearly. A decision that lives only in email will be questioned later.

Automation should remove guessing, not only clicks

Once the queue is visible, automation becomes safer. The goal is not to send more notifications. The goal is to remove guessing.

A useful approval automation should answer basic questions without a meeting:

  • What is waiting right now?
  • Who owns the next action?
  • Which requests are blocked by missing data?
  • Which decisions changed a record in Salesforce or the ERP?
  • Where do exceptions go when the normal route cannot continue?

This can be done with different tools. Some companies use Salesforce approvals. Some use ERP workflows. Some need a small integration layer between systems. The tool matters less than the rule: the queue must be visible, owned and tied to the system of record.

Questions to ask before rebuilding the workflow

Before choosing a tool, walk through one approval from last month and answer these questions.

  1. What exactly triggered the approval? If the trigger is not clear, automation will create noise.
  2. What data did the approver need but not have? That data belongs in the request, not in a follow-up message.
  3. Who owned the request at each moment? Any gap is where work can stall.
  4. What happened when the normal path failed? If the exception path is informal, it should be designed before it is automated.
  5. Where was the final decision recorded? If the answer is email, the operating system and the audit trail are separate.

The answer may show that you do not need a large project. You may need one workflow with clear fields, clear ownership and a small connection back to the system that carries the order.

The queue is the control point

For Swiss and DACH B2B companies, approvals often sit between departments that already work carefully. Sales wants the order. Finance wants control. Operations wants a reliable handoff. The friction appears between them.

That is why the queue matters. It is where responsibility moves from one team to another. If the queue is invisible, the company depends on reminders and memory. If the queue is visible, leaders can see what is waiting, why it is waiting and what should happen next.

The approval itself may take one minute. The uncertainty around it can take days. Fix the queue first.
